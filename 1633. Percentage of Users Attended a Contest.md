# 1633. Percentage of Users Attended a Contest
LeetCode: https://leetcode.com/problems/percentage-of-users-attended-a-contest/ · Easy

## Problem
For each contest, find the percentage of all users who registered for it, ordered by percentage descending, then `contest_id` ascending.

**Users**
| Column | Type | Notes |
|---|---|---|
| user_id | int | primary key |
| user_name | varchar | |

**Register**
| Column | Type | Notes |
|---|---|---|
| contest_id | int | part of primary key (contest_id, user_id) |
| user_id | int | part of primary key |

**Example**
```
Users: (2, Alice), (6, Bob), (7, Alex)
Register: (215, 6), (215, 7), (207, 7)

Output:
contest_id | percentage
215        | 66.67
207        | 33.33
```
Contest 215 has 2 of 3 users registered (66.67%); contest 207 has 1 of 3 (33.33%).

## Solution
```sql
SELECT r.contest_id,
       ROUND(
           COUNT(r.user_id) * 100.0 / (SELECT COUNT(*) FROM Users),
           2
       ) AS percentage
FROM Register r
GROUP BY r.contest_id
ORDER BY percentage DESC, contest_id ASC;
```

1. `COUNT(r.user_id)` per contest works cleanly because `(contest_id, user_id)` is a primary key, so no user can register twice for the same contest.
2. The scalar subquery `(SELECT COUNT(*) FROM Users)` runs once and supplies the fixed denominator, the total user count (3 here), without needing a join.
3. Multiplying by `100.0`, not `100`, forces decimal division instead of integer truncation before `ROUND()` rounds to two places.
4. Contest 215: 2/3 × 100 = 66.67; contest 207: 1/3 × 100 = 33.33. `ORDER BY percentage DESC` puts 215 first.

A `CROSS JOIN` between `Users` and `Register` plus `COUNT(DISTINCT ...)` on both sides reaches the same answer, but it builds the full Cartesian product first and throws most of it away with `DISTINCT`, so it's worth knowing but not worth reaching for over the subquery version.

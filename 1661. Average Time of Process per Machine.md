# 1661. Average Time of Process per Machine
LeetCode: https://leetcode.com/problems/average-time-of-process-per-machine/ · Medium

## Problem
For each machine, find the average time a process takes to run, where processing time is `end timestamp - start timestamp`. Return `machine_id` and `processing_time` rounded to 3 decimal places.

**Activity**
| Column | Type | Notes |
|---|---|---|
| machine_id | int | |
| process_id | int | |
| activity_type | enum | 'start' or 'end' |
| timestamp | float | |

`(machine_id, process_id, activity_type)` uniquely identifies a row.

**Example**
```
Activity:
machine_id | process_id | activity_type | timestamp
0          | 0          | start         | 0.712
0          | 0          | end           | 1.520
0          | 1          | start         | 3.140
0          | 1          | end           | 4.120
1          | 0          | start         | 0.550
1          | 0          | end           | 1.550

Output:
machine_id | processing_time
0          | 0.894
1          | 1.000
```
Machine 0 ran two processes: 1.520-0.712=0.808 and 4.120-3.140=0.980, averaging to 0.894. Machine 1 ran one process: 1.550-0.550=1.000.

## Solution
```sql
SELECT a1.machine_id,
       ROUND(AVG(a2.timestamp - a1.timestamp), 3) AS processing_time
FROM Activity a1
JOIN Activity a2
    ON a1.machine_id = a2.machine_id
   AND a1.process_id = a2.process_id
WHERE a1.activity_type = 'start'
  AND a2.activity_type = 'end'
GROUP BY a1.machine_id;
```

1. The self join pairs up each process's start row (`a1`) with its end row (`a2`) by matching on both `machine_id` and `process_id`, so a process only ever gets matched to itself.
2. The `WHERE` clause pins `a1` to the 'start' side and `a2` to the 'end' side, which is what turns a symmetric join into a directional start-to-end pairing. Without it, the join would also match end-to-start and start-to-start.
3. `a2.timestamp - a1.timestamp` gives the duration of a single process; `AVG()` then averages those durations per machine after `GROUP BY machine_id`.
4. `ROUND(..., 3)` satisfies the 3-decimal-place requirement in the output.

`LAG()` offers an alternative that skips the self join: partition by `(machine_id, process_id)`, order by `timestamp`, and pull `timestamp - LAG(timestamp)` so each 'end' row picks up the time since its matching 'start' row (the 'start' row itself gets `NULL`, since it has no predecessor in its partition, and gets filtered out with `WHERE process_time IS NOT NULL`). It reads more like "diff against the previous row" than "match two halves of a pair," which can be cleaner if a process ever had more than two activity rows.

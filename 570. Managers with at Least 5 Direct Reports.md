# 570. Managers with at Least 5 Direct Reports
LeetCode: https://leetcode.com/problems/managers-with-at-least-5-direct-reports/ · Medium

## Problem
Find managers who have five or more people reporting directly to them. Return just their names, any order.

**Employee**
| Column | Type | Notes |
|---|---|---|
| id | int | primary key |
| name | varchar | |
| department | varchar | |
| managerId | int | references Employee.id, null if no manager |

**Example**
```
Employee: (101, John, A, null), (102, Dan, A, 101), (103, James, A, 101), (104, Amy, A, 101), (105, Anne, A, 101), (106, Ron, B, 101)
Output: name = John
```
Five employees (Dan, James, Amy, Anne, Ron) all list John as their manager, meeting the "at least 5" threshold.

## Solution
```sql
SELECT m.name
FROM Employee e
JOIN Employee m
    ON e.managerId = m.id
GROUP BY m.id, m.name
HAVING COUNT(*) >= 5;
```

1. This is a self join: `e` stands for the employee side of the relationship, `m` for the manager side, joined on `e.managerId = m.id`.
2. Grouping by `m.id, m.name` collects every employee under the same manager into one group; `m.id` is in the `GROUP BY` (not just `m.name`) in case two managers ever shared a name.
3. `COUNT(*) >= 5` then keeps only managers whose group has 5 or more employees in it. In the example, John's group has exactly 5 rows (Dan, James, Amy, Anne, Ron), so he clears the bar.
4. Employees with no manager never appear as `e` here since a null `managerId` won't satisfy the join, so they don't pollute anyone's count.

A subquery version does the grouping directly on `managerId` (`SELECT managerId FROM Employee GROUP BY managerId HAVING COUNT(*) >= 5`) and then looks up those ids' names with `WHERE id IN (...)`. It skips the self join entirely, which can be cheaper on a large table, but needs `WHERE managerId IS NOT NULL` so a null managerId isn't treated as its own group.

# 585. Investments in 2016
LeetCode: https://leetcode.com/problems/investments-in-2016/ · Medium

## Problem
Sum `tiv_2016` for policyholders whose `tiv_2015` is shared with at least one other policyholder, but whose `(lat, lon)` location is unique among all policyholders.

**Insurance**
| Column | Type | Notes |
|---|---|---|
| pid | int | primary key |
| tiv_2015 | float | total investment value, 2015 |
| tiv_2016 | float | total investment value, 2016 |
| lat | float | latitude, never null |
| lon | float | longitude, never null |

**Example**
```
Insurance: (1, 10, 5, 10, 10), (2, 20, 20, 20, 20), (3, 10, 30, 20, 20), (4, 10, 40, 40, 40)
Output: tiv_2016 = 45.00
```
Pid 1 and 4 both share their `tiv_2015` value (10) with someone else, and both sit at locations no one else shares. Pid 2 and 3 sit at the same `(20, 20)` location as each other, so neither qualifies even though pid 3 also has a repeated `tiv_2015`. Only pid 1 and 4 count: 5 + 40 = 45.

## Solution
```sql
SELECT ROUND(SUM(tiv_2016), 2) AS tiv_2016
FROM Insurance
WHERE tiv_2015 IN (
    SELECT tiv_2015
    FROM Insurance
    GROUP BY tiv_2015
    HAVING COUNT(*) > 1
)
AND (lat, lon) IN (
    SELECT lat, lon
    FROM Insurance
    GROUP BY lat, lon
    HAVING COUNT(*) = 1
);
```

1. The two conditions are independent, so each gets its own subquery: one finds `tiv_2015` values that repeat (`HAVING COUNT(*) > 1`), the other finds `(lat, lon)` pairs that don't (`HAVING COUNT(*) = 1`). Same aggregate, opposite comparison.
2. Grouping by `lat, lon` together, not separately, is what makes `(20, 20)` register as one shared location instead of two coincidentally matching columns.
3. `(lat, lon) IN (...)` compares the pair directly against the pairs the subquery returns; MySQL treats this as a row-value comparison, no join needed.
4. In the example, `tiv_2015 = 10` repeats across pids 1, 3, and 4, so all three pass the first filter. Only pid 1 `(10,10)` and pid 4 `(40,40)` also pass the second filter, since pids 2 and 3 both sit at `(20,20)`.
5. `ROUND(..., 2)` formats the final sum as the problem asks.

A window-function version replaces both subqueries with `COUNT(*) OVER (PARTITION BY tiv_2015)` and `COUNT(*) OVER (PARTITION BY lat, lon)`, computed once per row instead of via separate lookups, then filters on those columns from an outer query. It reads a bit less like plain English than the `GROUP BY`/`HAVING`/`IN` version, but it's worth knowing since it avoids scanning the table twice.
